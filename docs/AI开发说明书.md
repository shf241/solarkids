# SolarKids AI 开发说明书

## 一、产品设计过程

项目初期先根据大作业要求确定 SolarKids 的产品定位：它不是单纯播放太阳系动画，而是面向儿童的互动教学产品。因此产品设计从“儿童怎么理解天体运行”出发，而不是从技术效果出发。

设计过程分为以下步骤：

1. 梳理课程要求：HTML5、CSS3、JavaScript、TypeScript、Canvas、SVG、LocalStorage、JSON、响应式布局。
2. 分析评分标准：产品设计、儿童友好体验、UI 视觉、Canvas/SVG 技术、功能完整性、AI 协同说明。
3. 确定核心场景：观察太阳系运行、点击行星学习知识、缩放视角、换肤、多语言和小游戏。
4. 设计信息架构：按照儿童认知顺序组织页面，而不是堆叠功能。
5. 设计用户流程：保证主要任务 5 步以内完成。
6. 拆分团队任务：产品交互、UI 响应式、Canvas 动画、数据存储与整合。

AI 辅助生成了初始分工方案、Git 协作说明、用户流程图结构和产品文档框架。学生根据课程要求和实际团队协作情况，对内容进行了筛选和调整。

## 二、用户分析过程

目标儿童用户年龄设定为 7-12 岁。该年龄段儿童通常具有以下特点：

- 更容易被图形、颜色、动画吸引。
- 喜欢点击、拖动、切换等直接操作。
- 对长段文字耐心较低。
- 对“太阳、地球、行星、彗星”等具体对象更容易理解。
- 需要明确反馈，例如按钮变化、行星高亮、卡片弹出。
- 需要允许试错，避免因为操作错误产生挫败感。

因此产品设计采取以下策略：

1. 主界面突出太阳、行星和轨道。
2. 主要操作使用图标和短文字。
3. 行星知识使用关键词和短句。
4. 所有核心任务控制在 5 步以内。
5. 动画保持平滑，不使用高频闪烁。
6. 设置入口保持简单，不提供复杂参数。
7. 小游戏以“拖动观察变化”为主，不要求理解公式。

## 五、用户体验优化过程

在用户体验设计中，项目围绕儿童用户做了以下优化：

1. 减少菜单层级：核心入口集中在主界面。
2. 缩短文字：知识内容以关键词和短句呈现。
3. 强化视觉反馈：点击行星后高亮并弹出知识卡片。
4. 保留重置按钮：让儿童可以放心尝试。
5. 动画平滑：使用 requestAnimationFrame 进行连续渲染。
6. 支持缩放：兼顾整体观察和局部观察。
7. 支持响应式：适配 PC、iPad、手机不同设备。
8. 保存设置：使用 LocalStorage 记录语言和皮肤选择。

## 六、设计决策说明

### 1. 为什么主界面以太阳系动画为核心

儿童理解天体运行最直接的方式是“看见运动”。因此主界面优先展示太阳、行星和轨道，而不是先展示文字说明。

### 2. 为什么使用 Canvas

行星公转、自转、彗星轨道和动态彗尾都需要连续绘制，Canvas 更适合作为核心动画渲染区域。

### 3. 为什么使用 SVG

按钮图标、天体符号、磁场线和部分装饰元素需要清晰缩放，SVG 适合做界面图形资源。

### 4. 为什么知识内容使用卡片

卡片可以让儿童在不离开主场景的情况下查看知识，减少页面跳转带来的认知负担。

### 5. 为什么核心任务限制在 5 步以内

儿童注意力持续时间较短，操作步骤过多会导致迷失。5 步以内可以保证任务清晰、可完成。

### 6. 为什么加分项分优先级

项目时间有限，必须先保证基础功能完整和稳定，再冲刺彗星、多语言、换肤、太阳风磁场和小游戏。

### 4. LocalStorage 设计

用户数据使用 `solarkids.user-state.v1` 单一根键保存，内容包括：

- `language`：`zh-CN` 或 `en`。
- `skinId`：与具体 CSS 和资源路径解耦的皮肤 ID。
- `learningProgress`：已访问行星和已完成任务的稳定 ID。
- `gameRecord`：游玩次数、成功次数、最好分和最近分。

采用单一根键和版本号的原因：

1. 可以整体读取、重置和升级。
2. 避免多个键只更新一部分造成状态不一致。
3. 数据结构改变时可以识别不兼容版本。

模块对损坏 JSON、字段缺失、非法语言、负数分数、Storage 禁用和容量异常进行安全回退。业务模块通过统一接口访问数据，不直接散落调用 `localStorage.setItem`。

### 5. 多语言设计

`src/data/language.json` 以语言代码为第一层，以稳定文案键为第二层。中英文使用完全相同的键集合，覆盖：

- 首页和常用操作。
- 设置、皮肤和小游戏。
- 儿童友好提示。
- 八大行星名称。
- 每颗行星3个关键词和2条科普短句。

英文文案优先使用短句和常用词。查询英文缺失键时先回退中文；两种语言都缺失时显示键名，避免界面出现 `undefined`。

### 6. 小游戏设计

小游戏核心不导入 DOM、Canvas 或 UI。成员3后续只需把 Canvas 坐标传给 `movePlanet`，并使用返回状态绘制反馈。

当前规则：

- 偏移0至5单位：`stable`，0分。
- 偏移大于5且小于60单位：`small`，50分。
- 偏移大于等于60单位：`large`，100分并完成。

该规则只用于帮助儿童观察“移动位置会带来轨道变化”的关系，是教学近似，不是精确引力或真实轨道仿真。这样处理避免在没有质量、速度、时间步长和引力方程的情况下给出错误的科学结论。

## 十、成员4独立思考与产品判断

1. 将 Storage 设计为可注入接口，使测试不依赖真实浏览器环境。
2. 使用稳定英文 ID 保存行星和皮肤，显示名称由词典负责，避免切换语言后数据失效。
3. 将多语言状态统一交给 Storage，避免 UI 维护第二份冲突状态。
4. 将小游戏计算写成纯函数，方便成员3接入并保证相同输入得到相同结果。
5. 对 Storage 异常采用非阻断回退，避免儿童因为浏览器设置问题无法进入应用。
6. 明确小游戏是教学近似，不使用未经验证的“真实引力模拟”宣传。
7. 将 UI、Canvas 和多设备测试标记为待整合，不用局部测试冒充整体验收。
